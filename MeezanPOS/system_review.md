### 🏗️ البنية المعمارية (Clean Architecture)

```
Domain/          ← الكيانات والواجهات والقيم الثابتة
Application/     ← الخدمات والـ ViewModels والواجهات التطبيقية
Infrastructure/  ← AppDbContext (EF Core + SQLite)
Presentation/    ← الـ Views (XAML) والمحولات
```

> [!TIP]
> المنظومة تتبع نمط **Clean Architecture** بشكل جيد مع فصل واضح بين الطبقات. الـ Domain لا يعتمد على أي طبقة أخرى، وهذا تصميم صحيح.

### ✅ نقاط القوة

1. **محرك مالي متين**: نظام الترحيل المالي (Posting Engine) متقدم ويدعم:
   - ترحيل فردي وجماعي (Batch)
   - تسوية وإقفال الفترات (Settlement & Lock)
   - فك الترحيل مع أسباب وتدقيق
   - آلية Self-Healing لمعالجة `DbUpdateConcurrencyException`
   - Triggers في SQLite لحماية السجلات المرحّلة

2. **أمان مقبول**:
   - BCrypt لتشفير كلمات المرور (work factor = 12)
   - ترحيل تلقائي لكلمات المرور القديمة (النص الواضح → BCrypt)
   - Mutex لمنع تشغيل أكثر من نسخة
   - Global Query Filter لـ Soft Delete
   - Audit Log لتتبع العمليات الحساسة

3. **بنية معمارية نظيفة**:
   - فصل Domain عن Infrastructure
   - Dependency Injection عبر `AppServiceProvider`
   - Interfaces لكل خدمة مالية

4. **نسخ احتياطي تلقائي** عند كل بدء تشغيل مع الاحتفاظ بآخر 10 نسخ

5. **ترحيل قاعدة بيانات ذكي** (`MigrateDatabase`) يضيف الأعمدة والجداول الناقصة تلقائياً

### ⚠️ نقاط الضعف والمخاطر

1. **ViewModels ضخمة جداً (God Objects)**:
   - [SalesViewModel.cs](file:///d:/Meezan sys/MeezanPOS/Application/ViewModels/SalesViewModel.cs) = **69KB** (1628 سطر)
   - [GeneralExpensesViewModel.cs](file:///d:/Meezan sys/MeezanPOS/Application/ViewModels/GeneralExpensesViewModel.cs) = **76KB**
   - [DailyJournalViewModel.cs](file:///d:/Meezan sys/MeezanPOS/Application/ViewModels/DailyJournalViewModel.cs) = **61KB** (1472 سطر)
   - [PostingService.cs](file:///d:/Meezan sys/MeezanPOS/Application/Services/PostingService.cs) = **51KB** (1078 سطر)
   
   > هذه الملفات تجاوزت الحد المعقول وأصبحت صعبة الصيانة والاختبار.

2. **Scoped Services مع Static Resolve**:
   - `AppServiceProvider.Resolve<T>()` يُستخدم في ViewModels بدون Scope، مما يعني أن الخدمات المسجلة كـ `Scoped` تعمل فعلياً كـ `Singleton`. هذا قد يسبب مشاكل في SQLite مع تعدد المعاملات.

3. **إنشاء `AppDbContext` مباشرة في ViewModels**:
   - `new AppDbContext()` يُستخدم في أماكن كثيرة بدلاً من الحقن. هذا يتعارض مع نمط DI ويصعّب الاختبار.

4. **لا توجد Unit Tests**:
   - لا يوجد مشروع اختبارات. المنطق المالي الحساس (ترحيل، تسوية، إعادة بناء الأرصدة) غير مغطى.

5. **SourceType كـ Magic Strings**:
   - `"DailyJournal"`, `"GeneralExpense"`, `"OwnerWithdrawal"` تُستخدم كنصوص حرفية. يوجد ملف [SourceTypeConstants.cs](file:///d:/Meezan sys/MeezanPOS/Domain/Enums/SourceTypeConstants.cs) لكنه غير مُستخدم بشكل كامل.

6. **WAL Mode يُفعَّل في مكانين مختلفين**:
   - مرة في `App.xaml.cs` (سطر 157) ومرة في `MigrateDatabase()` (سطر 179). يجب التوحيد.

7. **لوحة القيادة (Dashboard) بدائية**:
   - [DashboardViewModel.cs](file:///d:/Meezan sys/MeezanPOS/Application/ViewModels/DashboardViewModel.cs) حجمها فقط 2KB — تحتاج بناء حقيقي.

### 🚀 المقترح 1: لوحة قيادة تفاعلية متقدمة (Dashboard Pro)

**المشكلة**: لوحة القيادة الحالية بدائية ولا تعطي صاحب المطعم نظرة شاملة فورية على أداء العمل.

**المقترح**: بناء Dashboard احترافي يحتوي على:

| العنصر | التفاصيل |
|---|---|
| **ملخص اليوم** | إجمالي المبيعات، المصاريف، صافي الربح، رصيد الخزينة |
| **مقارنة الأداء** | مقارنة اليوم مع الأسبوع/الشهر الماضي (نسبة التغيير) |
| **رسوم بيانية** | ترند المبيعات اليومية (LiveCharts2)، توزيع المصاريف (Pie Chart) |
| **تنبيهات ذكية** | فواتير موردين مستحقة، عجز نقدي، ورديات غير مرحلة |
| **أفضل/أسوأ يوم** | أعلى مبيعات، أعلى مصاريف، أكبر فرق |
| **KPIs** | متوسط المبيعات اليومي، نسبة المصاريف من المبيعات |

**الجهد المقدّر**: متوسط (3-5 أيام عمل)  
**الأولوية**: 🔴 عالية — أكبر تأثير مرئي على المستخدم

### 🚀 المقترح 2: نظام إدارة المخزون (Inventory Management)

**المشكلة**: لا يوجد تتبع للمخزون. المشتريات تُسجل كمصاريف فقط دون ربطها بالأصناف. لا يمكن معرفة:
- ما هي الأصناف المتوفرة؟
- ما هو المخزون الحالي لكل صنف؟
- ما هي تكلفة البضاعة المباعة (COGS)؟

**المقترح**: إضافة وحدة مخزون تشمل:

```
Domain/Entities/
  ├── InventoryItem.cs        (اسم الصنف، الوحدة، الحد الأدنى)
  ├── StockMovement.cs        (وارد/صادر/تعديل + المصدر)
  └── StockCount.cs           (جرد فعلي)

Application/Services/
  └── InventoryService.cs     (إدخال/إخراج/جرد/تنبيهات)
```

| الميزة | التفاصيل |
|---|---|
| **بطاقة الصنف** | اسم، وحدة قياس، حد أدنى، فئة |
| **حركات المخزون** | وارد (من فاتورة مورد)، صادر (مبيعات/استهلاك)، تعديل |
| **ربط بالمشتريات** | عند إدخال فاتورة مورد → تحديث المخزون تلقائياً |
| **الجرد الفعلي** | مقارنة الكمية الفعلية بالدفترية وتسجيل الفروقات |
| **تنبيهات** | إشعار عند وصول صنف للحد الأدنى |

**الجهد المقدّر**: كبير (7-10 أيام عمل)  
**الأولوية**: 🟡 متوسطة — قيمة عالية لكن جهد كبير

### 🚀 المقترح 3: نظام الحساب الختامي والتقارير المالية (Closing Account)

**المشكلة**: لا يوجد تقرير ختامي شامل يُلخص الوضع المالي لفترة محددة. صاحب المطعم يحتاج:
- قائمة الدخل (Revenue vs Expenses)
- ميزان المراجعة
- تقرير الأرباح والخسائر

**المقترح**: بناء وحدة الحساب الختامي:

| التقرير | المحتوى |
|---|---|
| **قائمة الدخل** | إجمالي الإيرادات - إجمالي المصاريف = صافي الربح/الخسارة |
| **تحليل المصاريف** | تفصيل بالفئة (مشتريات، أجور، غاز، فحم، صيانة...) |
| **تقرير الموردين** | إجمالي المشتريات والمدفوعات والأرصدة لكل مورد |
| **تقرير الخزينة** | رصيد أول المدة + الوارد - الصادر = رصيد آخر المدة |
| **ملخص تنفيذي** | صفحة واحدة PDF بأهم المؤشرات والرسوم |

**الجهد المقدّر**: متوسط (4-6 أيام عمل)  
**الأولوية**: 🔴 عالية — ضرورة محاسبية

**المشكلة**: لا يوجد نظام إشعارات يُنبه المستخدم للأحداث المهمة مثل:

- مبالغ مورد تجاوزت حداً معيناً

| **تنبيهات مالية** | إذا تجاوز عجز الخزينة مبلغ محدد |

  └── Notification.cs (Type, Message, IsRead, CreatedAt)

**الجهد المقدّر**: متوسط (3-5 أيام عمل)
